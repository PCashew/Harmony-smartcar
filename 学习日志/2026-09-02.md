# 2026-09-02 学习日志

## 今日主题

今天围绕智能小车的独立蓝牙遥控功能，完成了原始工程整理、Hi3861 与 STM32 双端固件准备、手机连接 JDY-16、串口链路诊断，以及 Hi3861 构建配置修复。最重要的收获是：手机显示“蓝牙已连接”只说明 BLE 无线链路建立成功，并不能证明控制数据已经经过 Hi3861 转发到 STM32。排查双主控系统时，必须把整条链路拆开验证。

## 1. 蓝牙遥控系统的数据链路

本项目的完整控制链路为：

```text
手机蓝牙串口 App
→ JDY-16 BLE 透明传输模块
→ Hi3861 UART1（9600，GPIO1 接收）
→ Hi3861 指令解析
→ Hi3861 UART2（115200，GPIO11 发送）
→ STM32 USART1
→ 电机闭环控制
```

Hi3861 接收单字节控制字符，并向 STM32 发送 6 字节电机控制帧：

```text
0xFC, 左轮方向, 左轮速度, 右轮方向, 右轮速度, 0xFD
```

手机端使用 HEX 模式时，常用指令为：

| HEX | ASCII | 功能 |
| --- | --- | --- |
| `57` | `W` | 前进 |
| `53` | `S` | 后退 |
| `41` | `A` | 左转 |
| `44` | `D` | 右转 |
| `4F` | `O` | 停车 |
| `49` | `I` | 设置速度 |
| `4B` | `K` | 设置较高速度 |

在 HEX 模式下，UTF-8、ASCII 等文字编码设置不会改变 `4B` 这样的原始字节发送结果。

## 3. 手机已连接但小车不动

手机 App 显示已经连接 `JDY-16`，HEX 发送记录中也出现了 `4B`，但小车仍然没有动作。此时不能继续反复修改手机编码或换行设置，因为已有证据说明手机端已经发送了正确字节。

用手拨动车轮时，车轮会向相反方向回弹。这说明 STM32、电机驱动、编码器和零速度闭环正在工作：当目标速度为零而车轮被外力转动时，控制器会施加反向力矩纠正偏差。但这只能证明 STM32 控制环运行，不能证明蓝牙指令已经到达 STM32。

因此，排查重点转向两段内部串口：

1. JDY-16 到 Hi3861 的 UART1。
2. Hi3861 到 STM32 的 UART2。

## 4. 使用 USB 串口定位真实故障

将底板 SW2 切换到 `[3861]`，通过 CH340 的 COM5 以 `115200-8-N-1` 读取 Hi3861 启动日志。旧固件输出：

```text
ble uart OK!Failed to init uart! Err code = -1
```

这条日志给出了直接证据：

- `ble uart OK!`：连接 JDY-16 的 UART1 初始化成功。
- `Failed to init uart!`：连接 STM32 的 UART2 初始化失败。
- 原程序在 UART2 初始化失败后立即 `return`，因此蓝牙控制线程根本没有创建。

这就是“手机能够连接并发送，但小车完全没有反应”的真正原因。

## 5. Hi3861 构建配置修复

继续检查 Hi3861 SDK 的 `usr_config.mk`，发现原构建配置存在两个关键问题：

```text
CONFIG_AT_SUPPORT=y
# CONFIG_UART2_SUPPORT is not set
```

其中：

- UART2 支持被关闭，导致 Hi3861 无法建立与 STM32 的通信串口。
- AT 服务占用 UART1，可能与 JDY-16 的蓝牙数据接收发生竞争。

修复后的必要配置为：

```text
# CONFIG_AT_SUPPORT is not set
CONFIG_UART2_SUPPORT=y
```

重新编译后生成了新的 `Hi3861_BluetoothControl_allinone.bin`，并保留旧故障固件作为对照备份。以后重新搭建或清理 SDK 构建环境时，不能只复制 `Control.c` 和 `BUILD.gn`，还必须检查 SDK 外设配置。

## 6. 烧录后的实机验证

新固件烧录完成后，通过 COM5 再次读取启动日志，得到：

```text
ble uart OK!uart OK!
```

日志中不再出现 `Failed to init uart`，证明 UART1 和 UART2 均已完成初始化，蓝牙控制任务具备正常运行条件。

测试时需要注意：USB 线会继续给 Hi3861 供电，仅关闭小车电源开关不一定能让主控真正复位。可靠方法是按 Hi3861 的 RESET/RST 键；若必须彻底断电，则要同时断开 USB 和小车电源。

## 7. 今天形成的排障方法

面对“连接正常但执行器不动作”的问题，可以按下面顺序定位：

```text
确认手机发送的原始字节
→ 确认 BLE 模块已经连接
→ 读取 Hi3861 启动和错误日志
→ 检查 UART1/UART2 初始化结果
→ 检查 Hi3861 发出的控制帧
→ 检查 STM32 是否解析帧
→ 最后检查电机驱动与机械部分
```

这比同时修改 App、蓝牙模块、Hi3861 和 STM32 更有效。每一步都要寻找可观察证据，例如发送记录、启动日志、串口帧、LED 状态或编码器反馈。

## 今日总结

今天完成了独立蓝牙遥控工程和固件的整理，并从实机日志中定位出 UART2 初始化失败这一根因。问题并不在手机输入，也不在 UTF-8 编码，而在 Hi3861 SDK 的外设构建配置。通过开启 UART2、关闭占用 UART1 的 AT 服务、重新编译和烧录，最终获得了 `ble uart OK!uart OK!` 的正确启动结果。

这次调试让我进一步理解了“编译成功、蓝牙连接成功、控制链路成功”是三个不同层次的状态。双主控项目必须分别验证无线链路、Hi3861 串口和 STM32 执行链路，不能根据单一现象推断整套系统正常。
