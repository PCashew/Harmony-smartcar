## 1. 源码中文乱码与编码统一

在 Visual Studio/VS Code 打开旧工程时，中文注释出现了 `ʹ�ܶ˿�ʱ��` 和 `锟斤拷` 等乱码。问题根源是文件原本采用 GBK/GB18030 编码，却被当作 UTF-8 打开或保存。

正确处理方法是：

1. 发现乱码后先不要保存文件。
2. 使用“通过编码重新打开”，优先尝试 `GB 18030` 或 `GBK`。
3. 中文恢复正常后，再“通过编码保存”为 UTF-8。
4. 如果文件已经在乱码状态下保存，应从 Git 历史、本地历史或备份恢复，不能依靠再次转码完整还原。

例如，今天识别并恢复了下面这条注释：

```c
//使能端口时钟
```

这让我认识到，`锟斤拷` 往往意味着原始字符已经在错误转码中丢失。项目统一使用 UTF-8，并在转换前保留 Git 版本，是避免源码注释损坏的可靠方法。

## 2. Hi3861 与 STM32 双主控分工

本次智能小车由两块控制器协同工作：

| 控制器 | 主要职责 |
| --- | --- |
| Hi3861 | 红外桌沿检测、HCSR04 测距、SG90 扫描、避障决策与串口指令发送 |
| STM32 | 电机驱动、左右编码器采集、速度闭环、距离控制、转角控制与灯光显示 |

Hi3861 负责感知和决策，STM32 负责实时运动控制。相比让一个控制器同时处理所有任务，这种分工能让传感器逻辑和电机闭环更清晰，也便于分别编译、烧录和排查问题。

## 3. 编码器闭环直行与精确转向

小车没有陀螺仪，因此直行和转角主要依靠左右轮编码器。直行时不能只给两侧相同 PWM，因为电机、轮胎摩擦和机械阻力存在差异。更合理的方法是在固定控制周期内比较左右编码器增量：

```c
syncError = leftEncoderDelta - rightEncoderDelta;
correction = Kp * syncError + Ki * accumulatedError;

leftTarget  = baseSpeed - correction;
rightTarget = baseSpeed + correction;
```

左右轮再分别通过速度 PI 调节 PWM，从而补偿两轮速度差。转向时累计编码器脉冲，让左右轮反向运动到目标行程，而不是用固定延时估算 90°。

原地转向时，每个轮子的理论行程为：

```text
distance = 轮距 × 目标角度（弧度）÷ 2
```

但理论轮径和轮距不能直接保证实车精度。轮胎压缩、打滑和转向惯性都会造成误差，因此还需要通过多次 360° 或 90° 实测，标定有效轮距、轮径和停止提前量。编码器能显著提高重复性，但无法感知轮胎已经打滑，这也是后续需要继续解决的问题。

## 4. 红外防跌落与安全优先级

红外对管负责判断车轮前方是否仍有桌面。完整的防跌落流程为：

```text
检测到桌沿
→ 立即停车
→ 后退到左右红外都重新检测到桌面
→ 扫描转向区域
→ 选择安全方向
→ 编码器闭环转向
→ 再次确认红外安全
→ 继续前进
```

红外检测必须拥有最高优先级。只要任一探头判断存在跌落风险，系统就应中断普通巡航和避障动作。若串口失联、测距持续失败、无法退回桌面或两侧都没有安全空间，则保持停车，不能强行转向。

## 5. 舵机超声波避障

今天进一步明确了 HCSR04 超声波的作用：它适合检测前方和转向区域中的障碍物，但不能可靠判断下方是否还有桌面。防跌落由红外负责，超声波负责防碰撞和比较可行方向。

超声波安装在 SG90 舵机上后，可分别测量左、中、右三个方向：

```text
左侧距离  dLeft
正前距离  dFront
右侧距离  dRight
```

测量时应等待舵机稳定，并对每个方向连续采样多次，使用中位数过滤偶发异常。左右距离差达到一定阈值后，才认为某侧明显更宽；若两侧都太近，则保持停车。

调试中发现，原有程序只在红外发现桌沿并完成后退后才扫描超声波，正常前进时并没有持续测量，因此手挡在传感器前方时小车不会停车。随后将逻辑调整为巡航期间持续检测正前方：发现障碍物后先停车，再扫描左右并选择安全方向转弯。

## 6. 四种运动灯光状态

为了让小车当前动作更直观，今天为 STM32 增加了四种灯光状态：

- 前进：显示前进灯光。
- 左转：显示左转灯光。
- 右转：显示右转灯光。
- 倒车：显示倒车灯光。

灯光应由统一的运动状态更新，避免在多个控制分支中重复设置。这样既便于观察状态机是否按预期运行，也能在调试时快速区分“决策没有发出”“串口没有收到”和“电机没有执行”三类问题。

## 7. 编译、固件与 HiBurn 烧录

今天分别完成了两端工程的编译：

- STM32 工程通过 Keil 编译，结果为 0 Error、0 Warning，生成 `.hex` 固件。
- Hi3861 工程在 Ubuntu 的 OpenHarmony 环境中编译成功，生成 `.bin` 固件。

双板系统需要分别烧录，不能只更新其中一块：

1. 使用 STM32 下载工具将 `STM32_PrecisionMotion.hex` 烧录到 STM32。
2. 使用 HiBurn 将 `Hi3861_wifiiot_app_allinone.bin` 烧录到 Hi3861。
3. HiBurn 选择文件时，应进入 E 盘仓库的 `firmware/16_高精度桌面安全导航/` 目录并选择 `.bin` 文件；如果看不到文件，需要检查文件类型筛选和实际路径。
4. 烧录完成后复位两块控制器，首次测试先将车轮架空，确认方向、串口和急停逻辑正确。

## 8. 实车视频诊断

今天还通过两段实车视频检查了小车行为，确认了两个主要现象：

- 转向完成后车体仍继续偏移，说明编码器目标到达后的惯性、左右轮制动差异或机械打滑仍需标定。
- 斜前方障碍物在进入超声波主波束前存在明显盲区，单次正前方测距不足以覆盖斜置物体。

后续应从降低转向末段速度、加入停车稳定时间、校准左右轮制动差异，以及扩大舵机扫描范围和提高巡航扫描频率几个方向继续验证。
