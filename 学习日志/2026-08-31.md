# 2026-08-31 学习日志

## 今日主题

今天主要学习了 Hi3861 上的两类传感器实验：使用 AP3216C 采集环境光照强度，以及使用左右红外对管识别黑白区域。学习内容涵盖 I2C 传感器初始化、寄存器数据读取、GPIO 输入检测、CMSIS 定时器、OpenHarmony 组件配置，以及编译和固件生成流程。

## 1. AP3216C 传感器采集光照强度

AP3216C 是一款集成式传感器，可以同时采集以下三类数据：

- `IR`：红外数据。
- `ALS`：环境光照强度数据。
- `PS`：接近检测数据。

### 当前工程参数

| 项目 | 当前配置 |
| --- | --- |
| 通信方式 | I2C |
| I2C 控制器 | I2C0 |
| 设备地址 | `0x3C` |
| I2C 速率 | 400 kbit/s |
| 数据刷新周期 | 1 秒 |

程序首先调用 `AP3216C_Init()` 初始化 GPIO、I2C 和传感器工作模式，然后通过 `AP3216C_ReadData()` 一次读取 IR、ALS 和 PS 三组数据，并通过串口打印。

### 寄存器与数据组合

AP3216C 的三类数据分别保存在高、低两个寄存器中：

| 数据 | 低字节寄存器 | 高字节寄存器 |
| --- | --- | --- |
| IR | `0x0A` | `0x0B` |
| ALS | `0x0C` | `0x0D` |
| PS | `0x0E` | `0x0F` |

读取两个字节后，需要将它们组合成 16 位数据：

```c
value = ((uint16_t)data_H << 8) | data_L;
```

这一步让我进一步理解了传感器寄存器的数据组织方式：I2C 每次读取的是字节，而完整测量值通常需要按照芯片手册规定的格式进行拼接和位处理。

### OpenHarmony 任务

AP3216C 示例使用 `osThreadNew()` 创建采集线程，线程栈大小为 1024 字节，优先级为普通优先级。线程在循环中每隔 1 秒读取并打印一次传感器数据。

程序通过下面的宏注册启动入口：

```c
APP_FEATURE_INIT(i2c_ap3216c_demo);
```

OpenHarmony 启动后会自动调用该函数，不需要传统裸机程序中的 `main()` 入口。

## 2. 红外对管收发与黑白识别

红外对管实验使用小车左右两侧的 TCRT5000 模块检测地面反射情况。发射管发出红外光，接收端根据反射强弱输出数字电平，程序再读取 GPIO 电平判断当前区域是黑色还是白色。

### GPIO 配置

| 传感器 | Hi3861 引脚 | 方向 |
| --- | --- | --- |
| 左侧红外对管 | GPIO13 | 输入 |
| 右侧红外对管 | GPIO14 | 输入 |

初始化时先调用 `GpioInit()`，再使用 `IoSetFunc()` 将 GPIO13、GPIO14 复用为普通 GPIO，最后调用 `GpioSetDir()` 设置为输入模式。

当前代码采用以下判断关系：

```text
低电平：检测到黑色
高电平：检测到白色
```

程序分别读取左右传感器，并通过串口输出：

```text
left black / left white
right black / right white
```

### 周期定时读取

实验使用 CMSIS-RTOS2 软件定时器周期读取红外对管：

```c
id1 = osTimerNew(Timer1_Callback, osTimerPeriodic, &exec1, NULL);
osTimerStart(id1, timerDelay_1);
```

定时器到期后进入 `Timer1_Callback()`，再调用 `get_tcrt5000_value()` 读取左右 GPIO。与在线程中持续死循环相比，周期定时器可以让采样逻辑更清楚，也便于后续调整检测频率。

当前代码中 `timerDelay_1` 设置为 `5U`，同时注释说明 Hi3861 中 `1U=10ms`，因此实际周期应为约 50 ms，但旁边仍保留“10秒”的旧注释。后续需要根据循迹响应速度确定合理周期，并同步修正注释，避免调试时产生误解。

## 3. 工程配置与编译

两个实验分别使用独立的 `BUILD.gn` 声明静态库：

```text
TCRT      → static_library("TCRT")
AP3216C   → static_library("Ap3216c")
```

整理 AP3216C 目录时，驱动源码和头文件已经移动到工程根目录，但原来的 `BUILD.gn` 仍引用 `src/` 和 `include/`。今天将构建路径修改为当前实际结构：

```gn
sources = [
    "Ap3216c.c",
    "hal_bsp_ap3216c.c",
]

include_dirs = [
    ".",
]
```

由于两个实验都有各自的 OpenHarmony 启动入口，因此采用逐个启用、逐个编译的方式，避免把两个独立实验同时加入固件。

完整的 OpenHarmony 编译环境位于 Ubuntu 虚拟机：

```text
/home/harmony/harmony/code/code-1.0
```

编译命令为：

```bash
python build.py wifiiot
```

今天两个工程都成功出现以下结果：

```text
BUILD SUCCESS
ohos wifiiot build success!
```

生成的两个独立固件已经复制到 Windows：

```text
E:\Harmony-smartcar-builds\TCRT_Hi3861_wifiiot_app_allinone.bin
E:\Harmony-smartcar-builds\AP3216C_Hi3861_wifiiot_app_allinone.bin
```

烧录时一次选择其中一个固件，不能把两个固件同时烧录到开发板。

## 4. Windows、虚拟机与 GitHub 的关系

今天还明确了源码管理和编译环境之间的区别：

```text
Windows 仓库：编辑、整理和提交源码
GitHub：在 Windows 与 Ubuntu 之间同步代码
Ubuntu 虚拟机：运行完整 OpenHarmony 工具链并生成固件
HiBurn：在 Windows 中将固件烧录到 Hi3861
```

Windows 的 `E:\Harmony-smartcar` 目录本身没有 `build.py`，不能直接在 PowerShell 中执行 OpenHarmony 编译。正确流程是将代码同步到 Ubuntu，复制到 `applications/sample/wifi-iot/app/`，在根 `BUILD.gn` 中启用目标组件，再从 OpenHarmony 根目录执行编译。
